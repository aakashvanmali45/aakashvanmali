Making Every Token Parse

Study notes on grammar-constrained decoding — how PICARD, SynCode, XGrammar and IterGen steer a language model one token at a time so its output always fits a grammar, with no extra training.

Logits & masks · Grammars · Incremental parsing · DFA mask stores · Pushdown automata · Backtracking
math_area_sqrt(3\n)

A language model writing code is a bit like a fluent typist working with their eyes closed. It's fast, it's usually right, and every so often it forgets to close a bracket or invents a function that doesn't exist. Grammar-constrained decoding is the idea of watching over its shoulder, one keystroke at a time, and quietly taking away the keys that would make the program impossible to parse.

I'm learning this from four papers: PICARD (2021), SynCode (2024, published 2025), XGrammar (2024) and IterGen (2025). These notes start from zero — how a model picks a word at all — and build up one stage at a time. Each stage answers the question the previous one leaves open, and there are eight labs to play with along the way.

The summary I started with, and what I had to correct

Before reading the papers properly, my one-paragraph understanding was: during decoding, keep a Python parser's state and mask invalid tokens at each step. That guarantees syntactically valid output with zero extra training. XGrammar made this 100× faster. IterGen added backtracking — if semantic errors are detected, undo and regenerate from a checkpoint. That's a good skeleton. Reading carefully, each sentence needed a small but important correction:

What I thoughtMore precisely
"Maintain a Python parser state"Any language with a grammar works. PICARD was built for SQL. SynCode covers JSON, SQL, Go and a large subset of Python.
"Guarantees syntactically valid output"It guarantees every partial output can still become valid. If generation hits its token limit first, the output can still be cut off mid-program.
"Zero additional training"True — but you need the model's raw next-token scores at every step, which means open-weight models or APIs that offer a constrained mode.
"XGrammar made this 100× faster"Up to 100× faster at computing the mask, compared with earlier grammar engines. The model itself isn't faster; the constraint stops being the bottleneck.
"IterGen detects semantic errors"You write the checks ("is this table in the database?"). IterGen gives you a clean way to stop at a grammar symbol, inspect it, and undo exactly that piece.

01 How a language model writes, one token at a time

Everything in this topic happens in one small moment that repeats thousands of times: the model choosing its next token. So that's where to start.

Tokens. A model doesn't write letters or whole words. It writes tokens: chunks of text from a fixed list called the vocabulary. Common words get their own token (def, return); rare ones are split into pieces (math + _sqrt). Vocabularies are large — Llama 3's has about 128,000 tokens.

Logits. Given everything written so far, the model outputs one score per vocabulary entry: a logit. Higher means "more likely next". The softmax function turns those scores into probabilities that add up to 1:

Softmax with temperaturep(token i) = exp(zᵢ / T) / Σⱼ exp(zⱼ / T)zᵢ is token i's logit · T is the temperature: below 1 sharpens the distribution, above 1 flattens it.

Decoding. The rule for turning probabilities into a choice is called the decoding strategy. Greedy decoding always takes the most likely token. Sampling draws one at random according to the probabilities. Beam search keeps the k best partial outputs (the "beam") alive in parallel and extends each one. The chosen token is appended to the text, the text goes back into the model, and the loop repeats until the model emits a special end-of-sequence token (EOS) or hits a length limit. Because each token is chosen based on the ones before it, this is called autoregressive generation.

The one trick every paper here uses: masking

If a token must never be chosen, set its logit to −∞. Then exp(−∞) = 0, so its probability is exactly zero, and the remaining probabilities are rescaled to sum to 1 again. This is a mask: a yes/no flag per vocabulary entry.

Masked distributionp′(i) = mᵢ · p(i) / Σⱼ mⱼ · p(j)    mᵢ = 1 if token i is allowed, 0 if not

That's the entire mechanism. Every paper in these notes produces a mask at every step and hands it to an ordinary decoder. They differ only in how they decide which tokens to mask — and in how fast they can decide it for 128,000 tokens, thousands of times per answer.

Check: after masking, does the most likely remaining token change?

No. Masking removes options and rescales the rest by the same factor, so the order of the survivors never changes. What changes is which token is on top if you masked the previous favourite.

02 Why models write broken code, and three ways to respond

Language models are trained to produce likely text, not valid programs. Most of the time those overlap. When they don't, you get output a computer refuses to run. The papers give concrete numbers. A fine-tuned T5-3B model wrote SQL that failed with an execution error 12% of the time (PICARD). Asked for JSON, Llama-2-7B-chat produced invalid JSON for 98 of 100 prompts — mostly by wrapping it in chatty prose — and still 41 of 100 when told explicitly to output only JSON (SynCode).

There are three broad responses:

ApproachHowProblem
Ask betterPrompting, fine-tuning on more examplesHelps, but guarantees nothing
Filter afterwardsGenerate many outputs, keep the valid onesWasteful: earlier SQL systems needed beams of 16–100 candidates
Steer during generationReject an invalid token the moment it's proposedNeeds a fast, exact validity check at every step

All four papers take the third road. The idea that makes it work is one I had to sit with for a while:

Keep the prefix alive. Call a partial output alive if some continuation could still turn it into a valid program. print(len(x is alive; print(len x)) is dead — no ending can rescue it. If you only ever allow tokens that keep the output alive, and only allow EOS when the output is complete, then whatever finishes is valid. Nothing is ever repaired after the fact; a dead end is simply never entered.

Formally, the papers call the set of alive strings the prefix language of the grammar. A GPS analogy helped me: it doesn't wait until you've arrived somewhere wrong; it refuses every turn that leaves no route to the destination.

03 Grammars from zero: what "valid" means

"Alive" and "valid" need a precise definition, and that's what a grammar provides: a set of rules that describes exactly which strings belong to a language. I'll use the tiny calculator language from the SynCode paper's own walkthrough, because it's small enough to hold in your head:

# A tiny calculator language, written in the style SynCode uses (Lark EBNF) expr : term (("+" | "-") term)* term : factor (("*" | "/") factor)* factor : INT | FLOAT | "(" expr ")" | FUNC "(" expr ")" FUNC : "math_exp" | "math_sqrt" | "math_sin" | "math_cos" INT : /[0-9]+/ FLOAT : /[0-9]+\.[0-9]+/ # spaces are ignored

Note one rule in particular: "(" expr ")". Brackets can nest to any depth, so checking them means counting how many are open. A regular expression can't do that — it has no memory beyond a fixed number of states. Grammars that allow nesting need a stack. Remember that; it's the whole story of Stage 08.

04 The core loop: mask, pick, append, repeat

Put Stages 01–03 together and you have grammar-constrained decoding:

def constrained_generate(model, prompt, grammar, max_tokens): text = "" for _ in range(max_tokens): logits = model(prompt + text) # one score per vocabulary token mask = [grammar.alive(text + tok) for tok in vocab] # the expensive line mask[EOS] = grammar.complete(text) logits[not mask] = -inf tok = decode(logits) # greedy, sampling, beam: any works if tok == EOS: break text += tok return text

The model is untouched — no retraining, no new weights. Only the decoder changes. Below, a toy model is asked for the area of an equilateral triangle with side 2.27, in the calculator language. Its scores are scripted but realistic: it likes to invent a math_area function and to drift into a new line. Run it with the constraint off, then on.

A real model has around 128,000, generating a token every few milliseconds. Checking every token by re-parsing everything is hopeless at that scale. That speed problem is what Stages 06–08 are about. But first, one more complication.

05 The awkward part: tokens aren't grammar symbols

You might hope for a shortcut: ask the parser which terminal can come next, then allow only tokens of that terminal. It doesn't work, because model tokens and grammar terminals don't line up. The papers call this token misalignment.

Model tokens math_sqrt(3) *2.27
Terminals math_sqrtFUNC((3INT))**2.27FLOAT
One terminal can span several tokens (math_sqrt, 2.27), and one token can span several terminals ((3, ) *). The tokenization shown is illustrative.

Three consequences, each of which a real system has to handle:

A token can start mid-terminal. After math, the next token must continue a FUNC name. So the question isn't "which terminal is next?" but "which token strings can extend the unfinished math into something valid?"

A token can cross terminal boundaries. ) * finishes one terminal and starts another. Checking it means knowing what may come after the next terminal, not just the next one.

The last terminal can change type. SynCode's example is in Python: ret is an identifier, but one more token, urn, turns it into the keyword return. So the final piece of the output is never settled until something follows it. That's why Stage 03's remainder exists.

Misalignment is why early systems were either slow (checking every token by brute force) or occasionally wrong (approximating with terminals and missing edge cases). SynCode's main contribution is handling it exactly and fast. But the first big step came from PICARD.
06 PICARD (2021): check the model's favourites

PICARD — "Parsing Incrementally for Constrained Auto-Regressive Decoding", by Scholak, Schucher and Bahdanau at ElementAI/ServiceNow — targeted text-to-SQL. The task: given a question in English and a database's schema (its tables and columns), write the SQL query that answers it. The benchmark was Spider, where the databases at test time are ones the model never saw in training.

PICARD's answer to the speed problem is pragmatic: don't check all 32,000 tokens; check only the model's top few. At each step, for each hypothesis in the beam, take the k most likely tokens (k = 2 in their headline results), run each through a fast incremental parser, and give a score of −∞ to any that fail. Everything outside the top k is dismissed automatically. "Incremental" means the parser keeps its state from the previous step and only processes the new token, rather than re-reading the whole query.

Four levels of checking

PICARD's parser can check at four increasing levels of strictness. Anything that passes a higher level passes every lower one:

ModeWhat it checks
OffNothing.
LexingEach word is a real SQL keyword, operator, literal, or a table/column name that exists in the schema. Order doesn't matter.
Parsing without guardsThe query's grammar: clause order, missing from, and that table.column references actually match.
Parsing with guardsScope: every column used must eventually come from a table in the from clause. Checked as early as possible, so bad hypotheses leave the beam fast.

The last two are interesting: they already go beyond pure syntax into meaning, using the schema. Keep that in mind for IterGen. The lab below uses two real examples from the paper, plus three of my own, against two Spider schemas.

What PICARD achieved

Invalid SQL nearly disappeared: with PICARD, only 2% of T5-3B's outputs were unusable (cases where beam search ended without any valid query), against 12% execution errors without it. Exact-match accuracy on Spider's development set rose from 69.9% to 74.1% for T5-3B (schema only), and from 57.2% to 65.8% for T5-Base. With database content as extra input, T5-3B + PICARD reached 75.5% on development and 71.9% on the hidden test set — state of the art at the time. A detail I liked: without PICARD, bigger beams didn't help these models at all; with it, they did, because the beam was no longer wasted on invalid queries. The cost was modest: 2.5 → 3.1 seconds per question at beam size 4 on an A100.

Checking at every step mattered. When PICARD only checked hypotheses as they finished, it helped much less — the gap closing only at large beam sizes.

The limits that motivated what came next. PICARD's parser is hand-written in Haskell for SQL, so a new language means writing a new parser. It was evaluated with T5 only. And it only checks the top k: if all k of a hypothesis's favourites are invalid, that hypothesis simply dies, even if a valid token sat at rank k + 1.
07 SynCode (2025): precompute almost everything

SynCode (Ugare, Suresh, Kang, Misailovic and Singh at UIUC; arXiv 2024, TMLR 2025) asks for everything PICARD gave up: any grammar written as rules (in Lark EBNF), a mask over the whole vocabulary, proofs about what gets masked, and speed. Its key idea is that most of the work doesn't depend on what the model has written, so it can be done once, offline.

Step 1: split the output into "settled" and "remainder"

At each step, an incremental parser processes the output. Everything up to the last terminal is settled: its terminal types can't change any more. The last piece, which might still grow or change type (Stage 05's ret → return), is the remainder. From the parser's state, SynCode reads off the accept sequences: short sequences of terminals that could legally come next. SynCode uses sequences of length 1 or 2, which an LR(1) parser's tables give directly.

Example from the paper: the output so far is math_sqrt(3) * (2. The settled part ends at (, the remainder is 2, and accept sequences include [INT, )], [INT, *] and [FLOAT] — because the 2 might be a finished integer followed by something, or the start of a float.

Step 2: walk tiny machines instead of re-parsing

Each terminal is a pattern, and each pattern can be turned into a DFA (deterministic finite automaton): a handful of states joined by arrows labelled with characters. Reading a string means following arrows. If there's no arrow for the next character, the string has failed. A state is live if some path from it still reaches an accepting state.

Now the question "is token t okay?" becomes: start the first terminal's DFA, feed it the remainder, then keep feeding it the token's characters. If you end in a live state — or finish this terminal and carry on into the next one in the accept sequence — the token is okay.

The insight: the DFA mask store

Here's the part that made SynCode click for me. Once the remainder has been fed in, you're sitting in some DFA state q. Whether token t keeps the walk alive from q depends only on q, t and the next terminal — not on the program at all. So SynCode precomputes, offline, for every DFA state and every possible next terminal, a mask over the entire vocabulary. That table is the DFA mask store. At generation time, building the mask takes a few table lookups and a bitwise OR of the masks — a vectorized operation GPUs handle easily.

What SynCode guarantees

SynCode proves two properties. Soundness: it never masks a token that could lead to a valid program. To guarantee this, it slightly over-approximates — it allows a token if its beginning completes the accept sequence, without checking what comes after. Completeness: every token it allows really is safe, provided the accept sequences are longer than the longest token. With the short sequences used in practice, it's sound but not quite complete — in their experiments, that was rare enough not to matter.

The offline cost is real but one-off: building the mask store for Python or Go took 6–10 minutes and up to 1.9 GB of memory for vocabularies of 32,000–51,000 tokens, reused for every later generation with that model and grammar.

What it achieved — and the 4% it didn't

On JSON, SynCode produced zero syntax errors with both models tested. With Gemma-2-2B, the share of outputs matching their JSON schema rose from 41% to 99–100%. On Python and Go code completion, syntax errors fell by 96.07% on average. The leftover errors are the key to my first correction: every one was a program cut off at the maximum token limit. SynCode guarantees the partial output stays alive; it can't force the model to finish before it runs out of room.

Functional correctness barely moved: HumanEval pass@1 changed by at most a fraction of a point. Fixing syntax doesn't fix logic. On SQL, though, where many errors are syntactic, execution success for Llama-3.2-3B rose from 67.4% to 81.4% and accuracy from 28.6% to 34.9%.

Python has parts that aren't context-free — notably indentation. SynCode handles it with a separate tracker of which indentation levels are allowed next. It doesn't enforce meaning: a variable used before it's defined is still grammatical. That gap is IterGen's starting point.
08 XGrammar (2024): making nested grammars fast

XGrammar (Dong, Ruan, Chen and colleagues, from CMU and the MLC-LLM project; arXiv 2024, MLSys 2025) is a systems paper. Its target is a modern serving setup where a GPU produces thousands of tokens per second across a batch, and the grammar engine — running on the CPU — becomes the bottleneck. To see why, we need the nesting problem from Stage 03.

From DFAs to pushdown automata

A DFA has a fixed number of states, so it can't count unbounded nesting. A pushdown automaton (PDA) adds a stack. In XGrammar's design, each grammar rule becomes a small state machine. When a rule refers to another rule — an array containing an array — the PDA pushes the current position onto the stack and enters the inner rule. When the inner rule finishes, it pops back. The stack is the PDA's memory of "where I was before I went inside".

The trouble is that the stack can be arbitrarily deep, so there are infinitely many possible configurations. SynCode-style precomputation over every state is impossible. And checking 128,000 tokens against the full stack at every step is slow.

The insight: most tokens never look below the top

XGrammar splits the vocabulary at each position into two groups:

Context-independent tokens can be judged from the current position in the current rule alone. Inside a string, abc is fine and ] is not — whatever is on the stack. Context-dependent tokens finish the current rule and continue into whatever rule is underneath, so their validity depends on the stack. Inside a string, "] closes the string and then a bracket — fine only if the enclosing structure is an array.

Context-independent tokens can be decided ahead of time for every position in every rule and stored. XGrammar calls this the adaptive token mask cache ("adaptive" because it stores whichever of the accepted or rejected lists is smaller). At runtime, only the context-dependent tokens get checked against the real stack. In the MLC team's words, more than 99% of a mask usually comes straight from the cache. The rest of the engineering

Four more ideas push the remaining cost down. Context expansion looks at what can follow each rule wherever it's used, which turns many context-dependent tokens into cacheable ones. A persistent execution stack stores the many possible stacks (ambiguous grammars produce several at once) as a shared tree, so splitting, merging and rolling back are cheap. Rolling back matters for speculative decoding, where some guessed tokens get thrown away. Compiler-style automaton optimizations — inlining small rules, merging equivalent states — shrink the PDA. And the grammar work for step t+1 runs on the CPU while the GPU computes the model's forward pass, so it hides behind time that's being spent anyway.

What "100× faster" actually means

The paper reports up to 100× lower per-token mask-generation latency than existing grammar engines. In the MLC team's published benchmarks with Llama 3, mask generation was up to 3.5× faster on JSON-schema tasks and over 10× faster on general grammars. End to end in serving on an H100, it was up to 14× faster for JSON schema and up to 80× for general grammars, compared with other engines. The gap grows with batch size, because the GPU gets faster while a slow CPU-side engine doesn't. The headline goal is near-zero overhead: constrained generation at nearly the speed of unconstrained. XGrammar has since been integrated as a grammar backend into serving engines such as SGLang and vLLM.

09 IterGen (2025): undo when the meaning is wrong

Everything so far guarantees syntax. But SELECT COUNT(*) FROM employee_hire_evaluation is perfectly grammatical SQL that fails because that table doesn't exist. Meaning-level mistakes like this are called semantic errors, and a grammar can't see them. A masking approach also has no way back: once a wrong table name is written, a left-to-right decoder can only keep going.

IterGen (Ugare, Gumaste, Suresh, Singh and Misailovic, ICLR 2025; built on SynCode) adds the missing direction. The natural fix — undo the last few tokens — is awkward, because tokens don't line up with anything meaningful (Stage 05). IterGen's idea is to navigate by grammar symbols instead. It offers three operations:

CallMeaning
forward(symbol, n)Generate, grammar-constrained, until n more instances of that symbol are complete (e.g. one more table_name).
view(symbol)Return every piece of the output that is an instance of that symbol, so your code can check it.
backward(symbol, n)Erase the output back to just before the last n instances of that symbol.

You write the semantic check yourself — that's my correction from the start. IterGen makes it cheap to act on the result. Step through the lab: it plays a text-to-SQL session in the style of the paper's case study.

How it works underneath

The symbol position map. IterGen uses an LR parser, which builds structure bottom-up. It shifts terminals onto a stack, and when the top of the stack matches a rule's right-hand side, it reduces them into the rule's non-terminal. On every reduce, IterGen records where the new symbol starts (the first child's start) and ends (the last child's end). So it always knows which character span is which table_name, column_name or sentence.

One extra token. An LR parser only reduces once it can see the next terminal — you don't know a name has ended until something follows it. So to stop exactly at the end of a symbol, IterGen generates one lookahead token, confirms the symbol is complete, then removes that token. Users never see this.

The KV cache. When a Transformer generates, it stores the attention keys and values it computed for every earlier token so it doesn't recompute them — the KV cache. On backward, IterGen crops the cache at the right token position. Everything before the cut is reused; nothing is recomputed.

The decoding trace and the recurrence penalty. Greedy decoding is deterministic: undo and regenerate, and you'd get the same wrong name again. IterGen keeps a tree of everything it has generated, and multiplies the score of previously chosen tokens by (1 − γ)α, where α is how many times that token has been backtracked. This pushes it down a different branch. The paper used γ = 0.7 for SQL, and found accuracy flat across γ = 0.3–1.0 on their ablation, with no penalty clearly worse.

What it achieved

On Spider text-to-SQL, averaged over the nine models tested, accuracy went from 28.9% (unconstrained) to 35.2% (SynCode) to 41.6% (IterGen), and the share of queries that executed without error went from 50.3% to 63.7% to 75.8%. Average time per query was 0.81, 1.56 and 1.19 seconds respectively — IterGen was faster than SynCode on average; plausibly because, as the paper's error analysis shows, SynCode outputs sometimes ran on for many tokens after an invalid table name. In a privacy test, where models were prompted to reveal real email addresses from their training data, IterGen's "back up if this email exists in the leaked set" check took leaks from 45–67 per 100 prompts to zero for every model. On Vega-Lite chart specifications, accuracy rose by 17.8% over SynCode.

Limits. IterGen handles one sequence at a time, not batches. The recurrence penalty is a heuristic that can skew the first token after a backtrack. And a max_iter cap is needed, because a model might never find an acceptable answer. PICARD's guards were an early, SQL-only version of the same instinct — check meaning, not just form. IterGen makes it general and programmable.
10 Putting it together — and what none of them guarantee

Five things none of them guarantee

1. You need the logits. All of this happens inside the decoding loop. With a closed API that only returns text, you can't apply your own mask. You're limited to whatever constrained mode the provider offers.

2. The guarantee is only as good as the grammar. Real grammars are big, and "a substantial subset of Python" is not Python. Non-context-free features like indentation need special handling.

3. Alive isn't finished. Every prefix is valid, but if the token budget runs out, the output is cut off — exactly SynCode's leftover 4%.

4. Masking changes the model's choices, not just its errors. Masking and renormalizing at every step isn't the same as asking "of all valid programs, which does the model prefer?" A model can be steered down a path it would have rated unlikely overall, simply because each step looked fine locally. Park et al. (NeurIPS 2024, "Grammar-Aligned Decoding") study this distortion and propose a fix. In practice it's usually a good trade, but it's a real effect.

5. Valid isn't correct. SynCode's near-unchanged pass@1 shows it: a perfectly parsable program can still compute the wrong thing. IterGen narrows the gap only for properties someone has written a check for.

Grammar-constrained decoding is one simple move — set the logits of tokens that would lead to a dead end to −∞ — and a decade of compiler theory deciding which tokens those are, fast enough not to matter. PICARD showed the move works, checking only the model's favourites with a hand-written SQL parser. SynCode made it general and exact by noticing that, after the remainder, a token's fate depends only on a DFA state, so almost everything can be precomputed. XGrammar carried that idea through nested, stack-based grammars by caching every token that never looks below the top of the stack. And IterGen added the one thing a left-to-right decoder can't do: go back, by grammar symbol, when a check you wrote says the meaning is wrong.

The corrections to my opening summary were the most useful part of studying this. The guarantee is about prefixes. The speed-up is about the mask, not the model. And semantic checking is something you program, not something you get for free.
