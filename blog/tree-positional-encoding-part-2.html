Retrofitting Trees into Pretrained Transformers

Study notes on how TreeGen (2020) and Bartkowiak & Graliński (2025) get tree positions into a model — and a practical mental model for building it yourself.

Pretraining · Grammar rules · Depth embeddings · Token–node alignment · Do-no-harm init
← Part 1 · Teaching a Transformer to see trees Part 2 · Retrofitting

Part 1 ended with a Transformer that reads code as a tree. Then I hit an obvious question I'd been avoiding: Peng et al. trained their model from scratch. Almost nobody does that anymore. Can you take a model that has already been trained — one that already knows a lot about code — and teach it about trees after the fact?

These notes follow that question through two papers. TreeGen (Sun et al., AAAI 2020) came first and showed the simplest place to put tree information. Bartkowiak & Graliński (2025) took that idea and bolted it onto a pretrained code model. After that, I try to turn everything from both parts into a mental model for actually building one. As before, nothing is assumed: every new idea gets built from the ground up, and there are five labs to poke at along the way.

Carried over from Part 1. Transformers are order-blind, so they need positional information. Code's real order is a tree (its AST), not a line. Peng et al. describe each node by its path from the root as a list of (sibling order, child count) coordinates, and feed that into attention twice: a global vector per node, and a local vector per parent–child edge. If any of that is new, Part 1 builds it step by step.

06 What "pretrained" means — and why it complicates things

The first wall in this part wasn't about trees at all. Both papers lean on words like pretrained, fine-tuning and masked language modelling as if everyone knows them. I half did. So, from the beginning.

A neural network is a large pile of numbers called weights. Training means nudging those numbers, millions of times, until the network's outputs get good at some task. Starting from random numbers, that takes enormous amounts of data and compute.

Pretraining is the trick of doing that expensive training once, on a huge generic task, so the weights soak up general knowledge. Fine-tuning is taking those already-trained weights and training them a little more on the task you actually care about. It's the difference between hiring someone who already reads code fluently and teaching someone the alphabet first.

The pretraining game: fill in the blanks

For code models, a common pretraining task is masked language modelling (MLM). Take a snippet, hide some of its tokens — typically around 15% — and ask the model to guess what was there:

def normalize(a, b): return a [MASK] b # the model should guess "+"

No labels need to be written by hand: the hidden token is the label. That's why it scales to millions of functions. To guess well, the model has to learn what code tends to look like — that an operator sits between two operands, that a variable defined above gets used below.

The model both papers' story leads to is CodeBERTa, a small model of this kind released by Hugging Face. It follows the RoBERTa recipe (a refined version of BERT) and was trained on CodeSearchNet, a large collection of functions from public code in six languages. The "small" version Bartkowiak & Graliński use has 6 Transformer layers and about 83.5 million weights.

Where the input enters: the embedding layer

This is the part that matters most for retrofitting, so it's worth slowing down. Before any attention happens, a RoBERTa-style model turns each token into one vector by adding three learned embeddings, then normalizing:

RoBERTa's input embeddingxᵢ = LayerNorm( word_emb(tokenᵢ) + position_emb(i) + type_emb(0) )word: what the token is · position: where it is in the sequence (Part 1's sequential position) · type: a segment marker that's effectively constant here · LayerNorm rescales the sum to a standard spread.

Every weight above this layer was trained on vectors made exactly this way. That's the whole problem in one sentence.

Why adding to a trained model is delicate

Suppose I add a fourth embedding — a tree position — into that sum. If its table starts with random numbers, every input vector suddenly shifts. The six layers above it were tuned for the old vectors and now receive something they've never seen. Two things can go wrong. The new signal can scramble the input so badly that training has to relearn what the model already knew (this loss of prior knowledge is called catastrophic forgetting). Or, if the new signal is too faint, the model can learn to ignore it.

So the goal of a retrofit is narrow: start exactly where the pretrained model was, then let the new structure grow in. Hold on to that sentence — it decides almost every design choice in Sections 08 and 10.

Why not just retrofit Peng's method? You can, but it's invasive. Peng et al. add new terms inside the attention score of every layer, each with its own projection matrices, and change the score's scaling. A pretrained model's attention was calibrated without any of that. Nothing makes it impossible — Section 10 sketches how — but it's surgery inside every layer rather than a change at the entrance. That contrast is what made the next two papers click for me.
07 TreeGen: writing code one grammar rule at a time

TreeGen (Sun, Zhu, Xiong, Sun, Mou and Zhang, AAAI 2020) isn't a retrofit — it's trained from scratch, on a small dataset. It's in these notes because it shows, very cleanly, the cheapest place to put tree information. Bartkowiak's paper reuses exactly that place five years later.

TreeGen's job is code generation: read a description in English and write the program. Its main benchmark, HearthStone, pairs the text of a card from the card game with the Python class that implements it — only 533 training examples, averaging about 83 code tokens each. Generation is harder than understanding in one specific way: the model has to produce a tree that doesn't exist yet. TreeGen's answer is to stop writing tokens and start writing grammar rules.

Grammar rules, from zero

A programming language's grammar is a set of rewriting rules. Each one says how a kind of node can be expanded into its children:

A grammar ruleα → β₁ β₂ … βₖα is the parent (a node that still needs expanding). β₁…βₖ are its children. Example: Assign → targets value.

Nodes that still need expanding are non-terminals. Nodes that are actual text in the program — a name like length, a number like 10 — are terminals. Writing a program then becomes a loop: find the leftmost non-terminal that hasn't been expanded, pick a rule for it, repeat until only terminals are left. Each pick is a classification over the list of possible rules. The order of the picks is the depth-first (pre-order) walk from Part 1.

Here's that loop for the tiny program length = 10, with a slightly simplified grammar in the spirit of the paper's own example. Step through it.

Two things are worth noticing in that table, and they're the two halves of TreeGen's idea.

Half one: a depth embedding at the input

TreeGen's AST reader is a stack of Transformer-style blocks that reads the rules generated so far. Each rule gets an input vector made of three added parts:

TreeGen's AST-reader inputinputᵢ = rᵢ + pᵢ + dᵢrᵢ: embedding of which rule it is · pᵢ: position embedding (when the rule was used — Part 1's sequential position) · dᵢ: depth embedding — a table lookup on the depth of the node α that the rule expands.

The paper's reasoning is the same one Part 1 opened with: a position embedding says when a rule was used, not where it sits in the tree. Look at rules 7 and 8 in the lab. They are neighbours in the sequence, yet the depth falls from 7 back to 5. That drop is the model's only direct hint that the left branch is finished and it has climbed back up to fill in value. Without dᵢ, it would have to infer the climb from the content of the rules alone.

Notice how cheap this is: one more embedding table, one more term in a sum, right where the data enters. Compare that with Peng's coordinate lists and attention terms. TreeGen's depth is much less information, but it costs almost nothing and touches nothing else.

Half two: tree convolution

Depth alone says how deep a node is, not who its relatives are. TreeGen adds a second mechanism inside the AST reader: tree convolution. A regular convolution mixes each item with its neighbours in a sequence. Tree convolution mixes each node with its ancestors.

The trick is an adjacency matrix M: a grid with Mⱼᵢ = 1 if node i is the parent of node j, and 0 everywhere else. Multiplying all node features by M hands every node its parent's features. Multiplying twice hands it its grandparent's.

Tree convolution (window of 3)Y′ = GELU( W · [ Y ; Y·M ; Y·M² ] )Each node's new features are a learned mix of itself, its parent and its grandparent. TreeGen uses a window of 3. The root has no parent, so it borrows its own features.

Once the lab has generated the whole tree, click a non-terminal node — say value, or row 8. The gold rows are what tree convolution mixes; the blue rows are what an ordinary sequence convolution would mix. For rule 8, the sequence neighbours are the rule that wrote the name "length" and the rule that follows it. The tree neighbours are the Assign and body rules that actually own it.

One design choice I found genuinely insightful: TreeGen puts tree convolution only in the first few blocks, not all of them. The authors' reasoning is that as vectors pass through more Transformer blocks, each node mixes in information from every other node and gradually loses its own identity. Structural mixing works best while each vector still mostly describes its own node.

The query is a path

To choose the next rule, TreeGen's decoder needs to know which node it's about to expand. It represents that node as the path from the root down to it — for Assign, that's root, Module, body, Assign. That's the gold path in the lab. If it looks familiar, it should: it's the same "describe a node by its route from the root" idea that Peng et al. turned into coordinate lists two years later.

Did it work?

On HearthStone, TreeGen generated the exact reference program for 31.8% of test cards, against 27.3% for the best earlier method. A plain Transformer managed 10.6%. That 21-point gap isn't all down to tree structure — the plain baseline also lacks TreeGen's character embeddings and rule encodings — but the ablations isolate some of it: removing tree convolution alone dropped exact-match accuracy to 27.3%.

What TreeGen hands to a retrofit. TreeGen has two kinds of tree machinery. Tree convolution is new architecture: you can't add it to a pretrained model without new layers and lots of retraining. The depth embedding is different. It's one table added into the input sum — and every pretrained Transformer already has an input sum. That's the door Bartkowiak walks through.
08 Bartkowiak: two small tables bolted onto CodeBERTa

Patryk Bartkowiak and Filip Graliński (Adam Mickiewicz University) published Seamlessly Integrating Tree-Based Positional Embeddings into Transformer Models for Source Code Representation at an ACL 2025 workshop. The pitch is right there in "seamlessly": take CodeBERTa-small, leave every layer alone, and add tree information at the input.

Two numbers per node

Their tree position keeps just two numbers for each node: its depth and its sibling index. The root is (1, 1). Every other node takes its parent's depth plus one, and its own position among its siblings:

Bartkowiak & Graliński's tree positionF(root) = (1, 1)
F(x) = ( depth of parent + 1,  iₓ )iₓ = x's index among its siblings. Each of the two numbers gets its own learned embedding table.

Set that next to Peng's description from Part 1. Peng keeps the whole path as a list of (sibling order, child count) pairs. Bartkowiak keeps only how deep you are and which child you are at the last step. That's lossy. In Part 1's A–F tree, nodes D and F are both "depth 3, first child", so they get identical positions here, while Peng's lists tell them apart. The trade is simplicity: two lookups per node, no lists, no padding, nothing new inside attention. (The tiny tree in the header shows exactly this collision on its bottom row.)

The problem nobody warned me about: tokens aren't nodes

Peng's and TreeGen's models consume AST nodes directly. CodeBERTa doesn't. It consumes subword tokens from a byte-pair-encoding (BPE) tokenizer: a scheme that splits text into frequent chunks, so a rare identifier like normalize might become normal + ize, and ): might be a single token. Token boundaries come from frequency statistics, not from the grammar. To give each token a tree position, you need to align tokens to nodes.

For parsing, the authors use Tree-Sitter, a fast parser that supports many languages. Every node it produces records exactly which span of the source text it covers, which makes alignment possible: a token gets the position of the node whose span contains it. The paper notes that Tree-Sitter's output aligns well with the tokenizer's but doesn't spell out the edge cases. Section 10 has a lab for exactly that.

Three ways to mix the new embeddings in

Now there are five embeddings for each token — word, position, type, depth, sibling — and they need to become one input vector. The paper compares three strategies:

StrategyWhat it doesTrade-off
SumAdd depth and sibling embeddings to the usual sum, like TreeGen.Cheapest. No way to balance old and new signals.
Weighted sumMultiply each embedding by a learnable weight before adding.Lets training turn each signal up or down.
ConcatenationStack the embeddings side by side into a longer vector, then a linear layer projects it back to the model's width.Most expressive. More parameters, and the projection is brand new.

Three lessons fell out of playing with that. First, plain sum with randomly initialized tables shifts the input a lot — in the toy, the tree part makes up around half of what goes in. Second, slide the starting values to zero and every strategy becomes harmless: the model begins as exactly the pretrained model, and gradients can still grow the tables from there. Third, concatenation is only safe if the new projection starts as a pass-through; start it random and the pretrained layers are reading a different language on step one.

A caveat on the lab. It's a picture of step one, not of training. The paper doesn't say how its new tables were initialized, and a model can recover from a rough start given enough training. The point is the direction of the risk, not a prediction of their numbers.

How they trained it

The recipe has two stages, and both are standard. First, continue MLM pretraining on CodeSearchNet, now with the tree embeddings switched on, so the model learns to use them. Then fine-tune on clone detection — given two snippets, decide whether they do the same thing — using a dataset of roughly 600,000 code pairs. Both stages ran for three epochs with the AdamW optimizer, a learning rate of 1 × 10⁻⁵ and batches of 32, over three random seeds.

The new tables add about 789,504 weights, under 1% of the model. A detail I worked out myself rather than read in the paper: that number is exactly 2 × 514 × 768, which is consistent with two tables shaped like RoBERTa's own position table (514 rows of 768 numbers).

The paper also describes a tree attention mask, meant to steer attention toward structurally related tokens. In their experiments it's applied only to special tokens and the details are thin, so I'm leaving it out of these notes.

Weighted sum wins both tasks, and the authors report seed-to-seed spread below 0.002. On MLM, all three strategies gain about half a point. On clone detection the picture is more mixed: weighted sum gains 0.14 points, plain sum loses a little, and concatenation loses more than a full point. That's a pattern the mixer lab would predict — concatenation introduces the most brand-new machinery.

Their most interesting plot, to me, tracks the learned weights in the weighted-sum model during training. The depth and sibling weights are strongest early and shrink over time, while the word-embedding weight grows. My reading: structure helps the model organize itself early, then content takes over.

An open question in my notes. The tables compare against "Original". I couldn't tell from the paper whether that baseline got the same extra MLM epochs on the same data as the tree versions. For a half-point gap, that matters: some of the gain could come from extra training rather than from tree positions. Their code is linked from the paper, so it's checkable. Until then, I'd describe the result as small, consistent and cheap, not as a measured effect of tree positions alone.
09 Three doors for structure

Putting all three papers side by side, I stopped thinking of them as competing methods. They're answers to one question — where does tree information enter the model? — and there are only three doors:

DoorWhere the tree entersWho uses itRetrofit-friendly?
1 · Input sumAn extra embedding added to each token's input vectorTreeGen's depth embedding; Bartkowiak's depth + siblingYes — every Transformer has an input sum
2 · Attention biasExtra terms added to the attention scores in every layerPeng's global β and local γPossible, but surgery in every layer
3 · Structural layersNew layers that mix nodes along tree edgesTreeGen's tree convolutionHard — new architecture needs real training

There's a rough law here: the deeper inside the model the door is, the more tree information it can carry — and the harder it is to add to a model that already exists. Peng's door carries full paths and parent–child relations; Bartkowiak's carries two numbers per token, but it opens without touching a single pretrained weight. 10 Building it: an implementation mental model

Reading papers, I kept nodding along. Then I tried to picture the actual tensors and realized I couldn't. This section is the mental model I built so that I could: what exists at each step, what shape it has, and where it typically goes wrong. The code is a sketch in Python with PyTorch and Hugging Face Transformers — enough to see the moving parts, not a tested library. Where I make a design choice the papers don't specify, I say so.

The whole thing is a six-step pipeline. Steps 1–4 happen in data preparation, before the model sees anything; steps 5–6 are the model and its training.

  1. ParseTurn source text into an AST whose nodes know their text spans.
  2. Position the nodesWalk the tree once and record each node's depth and sibling index (or Peng's full coordinate list).
  3. Tokenize with offsetsRun the model's own tokenizer and keep each token's span in the source text.
  4. Align and build tensorsGive every token the position of the node that covers it; clamp, pad and batch into integer tensors.
  5. InjectAdd the tree embeddings at the input (door 1), and optionally as an attention bias (door 2).
  6. Train gentlyStart as the pretrained model, verify that, then train.

Steps 1–2: parse and position

With Tree-Sitter's Python bindings, parsing and positioning take a dozen lines. Each node keeps its byte span, depth and sibling index:

import tree_sitter_python as tspython from tree_sitter import Language, Parser parser = Parser(Language(tspython.language())) tree = parser.parse(code.encode("utf8")) def walk(node, depth=1, sib=1, out=None): out = [] if out is None else out out.append((node.start_byte, node.end_byte, depth, sib, node.type)) for i, child in enumerate(node.children, start=1): walk(child, depth + 1, i, out) return out nodes = walk(tree.root_node) # [(start, end, depth, sibling, type), ...]

Tree-Sitter's tree includes punctuation and keywords as their own small nodes ("def", "(", ":"), which is useful: every character of the program belongs to some leaf.

In code, with one trap called out. Hugging Face's offsets count characters; Tree-Sitter's spans count bytes. For plain ASCII code they agree, which is exactly why the bug hides until someone's comment contains an accented letter or an emoji:


    
enc = tok(code, return_offsets_mapping=True, truncation=True, max_length=512)

def to_byte(c):                      # character offset -> byte offset
    return len(code[:c].encode("utf8"))

depth_ids, sib_ids = [], []
for s, e in enc["offset_mapping"]:
    if s == e:                         # special tokens have empty spans
        depth_ids.append(0); sib_ids.append(0); continue
    s, e = to_byte(s), to_byte(e)
    covering = [n for n in nodes if n[0] <= s and e <= n[1]]
    start, end, depth, sib, _ = max(covering, key=lambda n: n[2])   # deepest wins
    depth_ids.append(min(depth, MAX_DEPTH))
    sib_ids.append(min(sib, MAX_SIB))


    
This scans every node for every token, which is fine for a sketch and slow for a dataset. A real version walks tokens and leaves together in one pass. The min(…) calls are the clamping from Part 1: anything deeper or wider than the table goes in the last row.


    
Step 5: inject at the input, without touching the model


    
Here's the part that made "seamless" concrete for me. Hugging Face models accept inputs_embeds in place of token ids. If you compute the word embeddings yourself and add the tree term, RoBERTa still adds its own position and type embeddings and its LayerNorm on top. So door 1 needs no change to the model's code at all:


    
class TreeEmbeddings(nn.Module):
    def __init__(self, hidden, max_depth=64, max_sib=64):
        super().__init__()
        self.depth = nn.Embedding(max_depth + 1, hidden, padding_idx=0)
        self.sib   = nn.Embedding(max_sib + 1, hidden, padding_idx=0)
        nn.init.zeros_(self.depth.weight)          # do no harm: start as
        nn.init.zeros_(self.sib.weight)            # the pretrained model
        self.w = nn.Parameter(torch.ones(2))      # weighted-sum knobs

    def forward(self, depth_ids, sib_ids):
        return self.w[0] * self.depth(depth_ids) + self.w[1] * self.sib(sib_ids)

model = AutoModelForMaskedLM.from_pretrained("huggingface/CodeBERTa-small-v1")
emb   = model.roberta.embeddings
tree  = TreeEmbeddings(model.config.hidden_size)

inputs_embeds = emb.word_embeddings(input_ids) + tree(depth_ids, sib_ids)
position_ids  = create_position_ids_from_input_ids(input_ids, model.config.pad_token_id)
out = model(inputs_embeds=inputs_embeds, position_ids=position_ids,
            attention_mask=attention_mask, labels=labels)


    
Three details in there each cost me a while to see:


    
Zero init still learns. The tables start at zero, so on step one the model is exactly CodeBERTa. But the gradient reaching each table row is the weight w times the gradient of the loss — and w starts at 1 — so the rows start moving immediately. The weights w themselves get no gradient on step one (their gradient is proportional to the zero tables), and pick up as the tables grow. This is a simplified version of Bartkowiak's weighted sum, which also weights the word and position embeddings.


    
Pass position ids yourself. When given input_ids, RoBERTa computes position ids that skip padding. When given only inputs_embeds, it can't see the padding and numbers every slot sequentially. Computing them from input_ids the way RoBERTa normally does (the helper lives in transformers.models.roberta.modeling_roberta) keeps the pretrained position embeddings meaning what they meant.


    
Padding index 0. padding_idx=0 keeps row 0 at zero forever and stops it from learning, so special and padding tokens contribute nothing structural.


    
Step 5, door 2: what a Peng-style bias adds


    
If you can edit the attention code, Peng's global bias β from Part 1 is a learned L × L matrix added to each layer's scores before the softmax. As a shape-level sketch (one head, no batching):


    
# coord_ids: [L, D] indices into the 136-row coordinate table (0 = padding); D = max depth
H    = coord_emb(coord_ids)              # [L, D, 32]
a    = ln(lin(H.flatten(1)))             # [L, d]        Part 1, Eq. 6
beta = (a @ Wq_a) @ (a @ Wk_a).T          # [L, L]        Part 1, Eq. 8
scores = (q @ k.T + beta) / math.sqrt(2 * d_head)   # Peng also adds the local γ here


    
The same do-no-harm idea applies, with a catch I only found by working through the gradients. To make β start at zero, initialize one of WaQ or WaK to zero — not both. If both are zero, each one's gradient is multiplied by the other, so both stay stuck at zero forever. And note the scale: a pretrained model's attention expects division by √dhead, while Peng's formula divides by √(2·dhead). In a retrofit I'd keep the pretrained scaling, so the old part of the score is unchanged on step one.


    
Step 6: train gently, and check before you trust


    
Bartkowiak & Graliński train everything at a learning rate of 1 × 10⁻⁵. A pattern I'd try on top (my suggestion, not theirs): give the new parameters a higher learning rate than the pretrained ones, since they start from nothing while the backbone only needs small adjustments. PyTorch optimizers accept separate parameter groups for exactly this.


    
Most retrofit bugs are silent: the model trains, the loss goes down, and the tree signal is wrong or missing. So the last lab is the checklist I'd run before believing any result. Tick them off as you go.

    Part 1 asked how a Transformer can see code as a tree. Part 2 asked how to give that sight to a model that already exists. The answer I've ended up with is a map more than a method. Tree information can enter through three doors: the input sum, the attention scores, or new structural layers. TreeGen used the first and third while training from scratch. Peng et al. used the second, also from scratch, and carried the most information. Bartkowiak & Graliński used only the first — two small tables, under 1% more weights — precisely because it's the one door you can open in a pretrained model without touching what it already knows.
    

    
    The practical rules came down to a handful of sentences. Align tokens to nodes by span, deepest node wins, and mind bytes versus characters. Start every new component at zero so step one is the pretrained model, but never zero both halves of a product. Check that the structure is actually reaching the model before trusting any result. And read half-point gains carefully.
