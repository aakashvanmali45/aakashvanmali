Teaching a Transformer to See Trees

Study notes on tree positional encoding — why a flat sequence loses the shape of code, and how Peng et al. (2022) give every syntax-tree node a coordinate the attention layer can read.

AST · Tree positions · 2D coordinates · Global & local bias · Disentangled attention

It started with one sentence in a paper, something like: we replace sequential positional embeddings with AST-derived positional encodings. I knew Transformers had a thing called positional encoding, and that it had to do with order. That was the whole of it. What's an AST? Why throw away a perfectly good position embedding? What does a tree have to do with attention?

These are my notes from working through it properly: Rethinking Positional Encoding in Tree Transformer for Code Representation by Peng, Li, Zhao and Jin (EMNLP 2022), read from the ground up. I kept hitting walls, and every wall turned out to be a missing foundation. So the notes follow the order I had to rebuild them in — five stages, each one answering the question the last one left me with. Four small labs sit along the way; the tree builder in Stage 2 is the one to play with first.

01 Transformers can't tell who came first

The first wall was the simplest one. Two sentences: Dog bites man. Man bites dog. Same three words, very different news. Any child learns early that order carries meaning.

Self-attention doesn't get that for free. Every token builds its query, key and value from its own embedding, then compares itself against every other token. Nothing in that computation says which token was first. Shuffle the input and you get exactly the same outputs, shuffled the same way — the property is called permutation equivariance. To a bare attention layer, both sentences are the same bag of words.

Dogbitesman──▶{ bites, dog, man }
Manbitesdog──▶{ bites, dog, man }
Without positions, self-attention receives the same set of vectors for both sentences. Whatever it computes for "dog" is the same in both.

The original Transformer (Vaswani et al., 2017) fixed this by adding a positional encoding to every token: a vector that means "I am at position k".

Sequential positional encodinginput(k) = token_embedding(k) + position_embedding(k)A token at position 0 gets the "position 0" vector added; the one at position 1 gets the "position 1" vector, and so on.

Now "dog at position 0" and "dog at position 2" are different inputs, and the model can learn that subjects tend to come first. For natural language, that's most of what you need.

Then code shows up

if x > 0: y = x + 1 else: y = 0

As text, this has an order: token 1, token 2, token 3. But its meaning lives in its structure. The if owns a condition, a then-branch and an else-branch. y = x + 1 lives inside the then-branch. The two assignments to y are alternatives, not a sequence. "I am token #7" says none of that — not which branch you're in, not whose child you are, not how deep you're nested.

The idea in one sentence. A vanilla Transformer sees code as a flat string. A tree-position Transformer gives each node of the code's syntax tree a position that describes where it sits in that tree.
02 Code is a tree before it's a string

The next wall: the paper assumes you know what an AST is. I didn't, not really. When Python — or any compiler — reads your code, the first thing it does is parse it into a tree that captures its grammar. That's the abstract syntax tree. "Abstract" because it drops the cosmetic parts (colons, brackets, whitespace) and keeps only the structure. Here's x = a + b:

x = a + b, as a tree
steel = inner node · teal = leaf · gold = root
A note on drawing. To keep the trees readable I fold operators into their parent's label (BinOp + rather than a separate Add child), and I drop Python's outer Module wrapper for one-line examples in the prose. Python's own ast module keeps both. The lab below keeps Module, because real files have more than one statement. Every tree in these notes uses the same conventions, so the numbers always line up.

Every tree paper leans on the same small vocabulary, so I wrote it down once against this example:

One convention to pin down now, because it trips up the formulas later: I count the root as depth 1. That's the convention under which a node's position list in Stage 4 has exactly as many entries as its depth.

Each node carries two pieces of information. Its type says what kind of syntax it is — Assign, BinOp, Name, If, Call. Its value is the literal text, when there is one — x, a, 0. Structural nodes like Assign have no text of their own, so the paper gives them a placeholder value, <empty>. What the model actually receives for each node is the sum of the two embeddings:

Node inputxᵢ = type_embedding(Assign) + value_embedding(<empty>)

Flattening the tree

A Transformer eats sequences, not trees, so the tree gets linearized. The standard choice — and the one the paper uses for every model it compares — is depth-first order: visit a node, then each of its children left to right, recursively. For x = a + b that gives Assign, Name x, BinOp +, Name a, Name b.

And here's the catch the rest of these notes are about: once you flatten, the shape is gone. The sequence says BinOp + comes third. It doesn't say that Name a and Name b belong to it. You can watch this happen below — the chips under the tree are the sequence the Transformer actually gets, appearing in the order it reads them.

One trick: the virtual node

The root has no parent, which is awkward for a formula that describes every node relative to its parent. The paper's fix is a classic from algorithms textbooks: add a virtual node above the root. It isn't code; it's scaffolding. The root becomes child 1 of 1 of the virtual node, and now every real node has a parent. You'll see it drawn dashed in the Stage 4 explorer.

Stage 2 in five lines. Code parses into an AST. Nodes have a type and sometimes a value. Sibling order and the parent's child count say where a node sits among its siblings; depth says how far down it is. A Transformer receives a flattened, depth-first sequence. Tree positional encoding is how the shape gets put back.
03 What a flat position throws away

With trees in hand, I could finally put the two ideas of "position" side by side. Take a = b + c. A standard Transformer tokenizes it and labels each token with its index:

Tokena=b+c
Sequential position01234

That tells the model about order and about distance in the text. It says nothing about who belongs to whom. The tree-position Transformer also receives a flattened sequence — Assign, Name a, BinOp +, Name b, Name c — but every node carries extra information about where it sits:

NodeSibling orderParent's child countDepth
Assign11 (virtual node)1
Name a122
BinOp +222
Name b123
Name c223

Read across and the structure falls out. Name a and BinOp + are siblings under Assign. Name b and Name c are siblings one level deeper. Name a is the first child, BinOp + the second. None of that lives in a column of plain indices.

The pair of snippets that convinced me

This is where it stopped being abstract. In snippet A below, z = 2 runs after the if, always. In snippet B, it runs only when x is truthy. Two different programs, one indentation apart.

Now look at them as tokens. Strip the whitespace — many code tokenizers fold indentation into other tokens or drop it — and the two streams are identical: if x : y = 1 z = 2. Python's own tokenizer does keep a trace: it emits INDENT and DEDENT markers, and the only difference between A and B is where a single DEDENT lands. Toggle the layout tokens to see it.

One invisible token carries the whole change in meaning — a weak signal for a model to pick up from sequential positions alone. The trees leave no doubt. In A, the assignment to z is a sibling of the If: the second statement of the module, at depth 2. In B, it sits inside the If's body, at depth 4. The position lists printed under each tree differ in both length and content. We'll decode that notation in Stage 4.

Two ways to use a tree position

The paper uses tree positions in two complementary ways, and the difference ended up mattering a lot:

Global (absolute). Every node gets one position vector — a GPS coordinate in the tree. Any two nodes can compare coordinates, whether they're neighbours or on opposite sides of the tree.
Local (relative). Only nodes joined by an edge — a parent and its child — get a relation vector, which says "these two are adjacent, and here is which one is the parent."

Stage 5 is where both get built. For now, the summary I kept on a sticky note:

Example signal"I am token 7""I am child 2 of 3, at depth 4"

Inductive bias, in one paragraph

An inductive bias is an assumption built into a model that helps it learn. A CNN assumes nearby pixels are related, which is why it slides small filters around. A tree Transformer assumes code nodes are related through the tree. Tree positional encoding hands that assumption to a Transformer that would otherwise see a flat sequence — and hands it over as a soft bias. Every node can still attend to every other node; the tree only nudges the scores.

04 Peng's recipe: positions as lists of 2D coordinates

This is the technical heart of the paper, and the part I read most slowly. The idea fits in one breath: describe each node by the path from the root down to it, and at every step along the path, write down two numbers.

Eq. 1 — the 2D recursive descriptionF(x) = F(f(x)) + {(xᵢ, xⱼ)}   if x ≠ root
F(x) = {(1, 1)}                  if x = rootHere "+" means "append to the list".
SymbolMeaning
F(x)The position description of node x: a list of 2D coordinates
f(x)The parent of x
F(f(x))The parent's list — this is where the recursion lives
xᵢThe sibling order of x: is it the 1st, 2nd, … child?
xⱼThe total number of children of x's parent

So each coordinate reads as a short sentence: I am child xᵢ of xⱼ. A node inherits its parent's list and appends one sentence about itself. The root, thanks to the virtual node, is child 1 of 1, so F(root) = {(1, 1)}.

Two patterns jump out. The length of a list is the node's depth. And a list reads like directions from the root: the last coordinate describes the node's relationship to its own parent, and everything before it is the parent's address.

Why "lossless" is the right word

The paper makes a point I underrated on first read: a good description of a structure should be lossless. From the description alone, you should be able to rebuild the original exactly. Given every node's list, you can. A list minus its last coordinate is the parent's list. The last coordinate says which child the node is and how many siblings it has. Parents, children, their order and every branching factor are all recoverable.

Compare the earlier tree Transformer of Shiv & Quirk (2019), which recorded only sibling orders along the path: (1, 2, 1) rather than {(1,2), (2,3), (1,1)}. That works neatly for regular trees, where every node has the same number of children. ASTs aren't regular — an If has two or three children, a Call has as many as it has arguments. Without the second number, "first child" can't tell an only child from the first of five. The ablations back this up. On Python code completion, overall accuracy fell from 63.2% to 59.4% without the sibling order, and to 62.0% without the child count.

From coordinates to vectors

Each coordinate becomes a vector through an embedding table, the same way a word does. The paper tried two options: mapping the pair to a single table index, or embedding each number separately and combining them. It found no real difference and kept the single-index version. For node i, that gives a sequence of vectors:

Eq. 2 — the vector sequence of node iHᵢ = [ h(i1), h(i2), …, h(in) ]n = depth of node i · h(ik) = the vector for the k-th coordinate in F(i)
The question I got stuck on · 1
Where does 16 × 17 / 2 = 136 come from?

The paper caps the number of children at 16, so both numbers in a coordinate run from 1 to 16. My first instinct was 16 × 16 = 256 table entries. But almost half of those pairs are impossible: you can't be the 5th child of a parent with 3 children. The constraint is xᵢ ≤ xⱼ.

So count the valid pairs column by column. One pair when the parent has 1 child, two when it has 2, and so on up to sixteen when it has 16. That's 1 + 2 + … + 16, a triangle number: 16 × 17 / 2 = 136. The grid below is that triangle. Hover a cell, drag the cap, and select a node in the explorer above to see which cells its coordinates use.

Two practical details. Anything past the cap is clamped, so the 20th argument of a 25-argument call is stored as (16, 16). And with 32-dimensional coordinate vectors, the whole table is 136 × 32 ≈ 4,400 parameters — tiny. All of the paper's positional machinery together adds about 1.3M parameters, mostly projection matrices, which is small next to the 6-layer, 512-wide Transformer it sits in.

The question I got stuck on · 2
Is Hᵢ per node or per tree — and doesn't its size keep changing?

Per node. Every node gets its own Hᵢ. And yes, its length changes, because it equals the node's depth: the root's Hᵢ holds one vector, a node at depth 10 holds ten.

That's a problem for a linear layer, which wants a fixed-size input. The fix is mundane. Pick a maximum depth (16 in most of the paper's settings), pad short lists with zero vectors, and cut long lists down to their first 16 entries. Then concatenate. A depth-3 node becomes 3 real vectors plus 13 zeros; at 32 dimensions each, every node ends up as a 16 × 32 = 512-number vector. That's the row of 16 slots in the explorer.

05 Getting the tree into attention

Stage 4 left every node holding Hᵢ. Stage 5 is the part I'd originally skimmed: how those vectors actually change what the model attends to. There are two routes, global and local, and both end up as extra terms added to the attention score. First, the score they're added to:

Content attentionαᵢⱼ = (xᵢWQ)(xⱼWK)TPlain self-attention between node i and node j, from their type + value embeddings.

Global: one absolute vector per node

Eq. 6 — absolute tree positionaᵢ = LN( Linear( Concat(Hᵢ) ) )

Pad or truncate Hᵢ to 16 entries, concatenate them into 512 numbers, project to the model's hidden size with a linear layer, and normalize. The result, aᵢ, is the node's tree coordinate. It encodes the whole root-to-node path — every sibling order and child count along the way — and with it, the depth.

Eq. 8 — global position scoreβᵢⱼ = (aᵢWaQ)(aⱼWaK)T

βᵢⱼ is an attention score computed purely from where two nodes sit. Because each aᵢ is built from a full path, comparing two of them exposes the route between the nodes: how much path they share and where they branch apart. The paper is careful to say the model has the potential to capture these pairwise paths through the dot product. It isn't hard-wired; it's learned. This is the global bias — every pair of nodes gets one, near or far.

Local: a relation vector for each edge

Eq. 7 — relative tree positionrᵢⱼ = LN( Linear( ΣHᵢ − ΣHⱼ ) )   if j is i's parent, or i is j's parent
rᵢⱼ = 0                              otherwise

Only parent–child pairs get a non-zero vector; every other pair gets zero. The subtraction is the clever part. If j is the parent of i, then Hᵢ is just Hⱼ with one extra vector appended — the one for i's own coordinate. Sum both lists, subtract, and everything they share cancels:

Why the subtraction worksΣHᵢ − ΣHⱼ = h(in)The embedding of i's last coordinate: (sibling order of i, child count of j).

So rᵢⱼ says, in effect, "i is child 2 of 3 of j." It says one more thing too, which I got wrong on my first pass.

The asymmetry is a sign flip. Swap the roles and the subtraction runs the other way: ΣHⱼ − ΣHᵢ = −h(in). Same coordinate, opposite sign. So rᵢⱼ and rⱼᵢ start from mirror-image inputs, and that's how the model can tell which end of an edge is the parent. After the linear layer and normalization the two vectors aren't literally negatives of each other, but they begin from opposite sides.

The local vectors get their own linear and normalization layers, separate from the global ones. They enter attention like this:

Eq. 9 — local position scoreγᵢⱼ = (xᵢWQ)(rᵢⱼWrK)T + (rⱼᵢWrQ)(xⱼWK)TFirst term: given i's content, how relevant is its structural relation to j? Second term: the mirror question, from j's side.

Why "disentangled"?

The original Transformer adds position to content before attention, so a single projection has to serve both:

Mixed (vanilla)((xᵢ + pᵢ)WQ) ((xⱼ + pⱼ)WK)TExpands into content·content + content·position + position·content + position·position, all forced through the same WQ and WK.

Disentangled attention keeps content and position as separate streams with their own projection matrices, and adds up the dot products. Ke et al. (2020) and DeBERTa (He et al., 2020) argued that pushing words and positions through the same projection is a poor fit. γᵢⱼ is DeBERTa's relative form; βᵢⱼ follows Ke et al.'s untied absolute form. Peng et al.'s contribution is carrying both over from sequence positions to tree positions.

Putting it together

Eq. 10 — the full scoreAᵢⱼ = (1/√2) · (αᵢⱼ + βᵢⱼ + γᵢⱼ)
zᵢ = Σⱼ softmaxⱼ(Aᵢⱼ) · xⱼWV

Four dot products feed Aᵢⱼ, yet the scale is 1/√2, not 1/√4. The paper's reasoning: γ is non-zero only for a node's handful of neighbours, so for almost every pair only α and β contribute. One thing worth knowing before implementing it: the paper leaves out the usual 1/√d factor to keep the equations readable. In code, you still divide by √d as well.

Why both?

The ablations are the payoff of the whole design. With only the global bias, the model already beats almost every baseline; the same is true with only the local bias. With both, it does better still. The authors' explanation, which I found convincing: the global bias sees every pair but is soft and perhaps fragile. The local bias is precise, but a node only learns about its two-hop neighbourhood by stacking a second layer, its three-hop neighbourhood with a third. Local information is hard to lose; global information is wide. Each covers the other's weak spot.

Three checks before moving on

Two sibling nodes share a parent but have no edge between them. What is rᵢⱼ?

Zero. Only parent–child pairs get a relation vector. The siblings can still relate through βᵢⱼ: their absolute positions share everything except the last coordinate.

Node i is the 3rd of 4 children of j. Which embedding survives the subtraction in rᵢⱼ, and with which sign?

h(3, 4) — i's own last coordinate — with a plus sign. In rⱼᵢ the same embedding appears with a minus sign, which is what marks j as the parent.

A node sits at depth 20 and the max depth is 16. What happens to its Hᵢ?

It's truncated to its first 16 vectors — the ones nearest the root — before concatenation. The four deepest steps of its path are dropped from aᵢ. Its relation vectors to its parent and children still carry its own last coordinate.

∴ What the five stages add up to

Looking back, the trail was shorter than it felt. Transformers are order-blind, so they need positions. Code's real order is a tree, not a line, so sequential positions lose its parent–child and sibling structure. Peng et al. describe a node's place in the tree as a list of (sibling order, child count) coordinates — a description you can rebuild the whole tree from. Each coordinate is embedded through a 136-row table, padded to a fixed length, and turned into two signals: a global vector aᵢ that lets any two nodes compare positions, and a local vector rᵢⱼ that tells adjacent nodes exactly how they're related, and which of them is the parent. Both are added to ordinary content attention, disentangled, and the combination beats either half alone on code summarization and code completion.

The two questions that unlocked it for me were embarrassingly basic. Where does 136 come from? (A triangle, because you can't be child 5 of 3.) Is Hᵢ per node or per tree? (Per node, variable length, padded to 16.) If you got stuck in the same places, you're in good company.
