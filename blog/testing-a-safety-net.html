Building a Safety Net

Why every working app quietly rots without tests, and how to build a three-layer suite — from pure functions up to a real browser — for a small todo app I use every day.

Pytest · Playwright · Unit · API · E2E · Page Object Model · Fixtures

I built a small todo app for myself and used it for a week. It worked. Then I started thinking about adding a feature — and I realised I had no way to know, without opening my browser and clicking through every screen, that the thing I'd change wouldn't break something I already relied on. That question — how do you keep an app trustworthy as it grows — has an answer with fifty years of engineering behind it. You write tests.

This is a field notebook from the first pass at doing that properly. Not a certification, not a textbook, not a war story from production. Just a small app, a laptop, and a suite that grew from nothing to twenty-two tests across three layers. Read it as study notes: the reasoning matters more than any single line of code.

01 The app, and the question I couldn't answer

todo-companion is a local, self-hosted todo and daily-planning app. Type a task and Google's Gemini breaks it into subtasks with time estimates. A quick energy check produces a plan for the morning, afternoon and evening. At day's end, three short prompts capture what you actually got done. It's a FastAPI backend, a vanilla-JavaScript single-page frontend, and a SQLite file — nothing exotic.

Every developer who has built something small enough to actually use has felt the same thing: this works, today. And the moment you go to change one line, you realise you don't know what else in the app depends on that line. So you open the browser and click. You add a task. You mark it done. You delete it. You reload. You open the recurring-task flow. You cross your fingers and ship. That flow is called manual regression testing, and its cost per change grows every time you add a feature. Eventually it costs more than the change itself, and you either stop shipping or start shipping bugs.

02 Why tests earn their keep

A good test suite pays three dividends, and any one of them justifies the effort:

1. Trust. When you change something, you learn in seconds — not in production — whether you broke a promise the app was already making to its users.
2. A change alarm. Bugs caught before merge cost minutes to fix. The same bug caught by a user six weeks later costs hours, plus reputation. The suite is an early-warning system priced in your time.
3. A living spec. A well-named test is a sentence about what the app is supposed to do. Read together, they describe the app's intent better than any document you'll write and forget to update.

None of this is new. What's new for me — and probably for anyone learning testing seriously for the first time — is that these dividends only materialise if the suite is structured. A pile of tests written in the wrong shape gives you almost none of the three, and worse, gives you false confidence. So before writing a single test, you decide on a shape.

03 The shape: the test pyramid

The test pyramid is the most-referenced mental model in all of QA. Tests come in layers, each layer trading off speed against realism. The good shape has many tests at the bottom (fast, focused, cheap) and fewer at the top (slow, holistic, expensive). Tap or hover a layer below to see what each one is for.

The pyramid is a shape, not a rule. But the intuition is real: if the shape inverts — a few unit tests at the base, hundreds of end-to-end tests at the top — your suite becomes slow, flaky, and eventually stops running. So the discipline is to push every test as far down the pyramid as it can honestly go. Test the pure function in isolation first; test the HTTP endpoint next; only test the whole browser flow when nothing below could give you the same confidence.

04 Scaffolding: setting the rules before the first test

Before the first assertion, the framework itself needs configuring. Skipping this step is the number-one reason personal test suites rot within a month — someone runs the tests slightly differently, gets a different result, blames the code, and stops trusting the suite. The fix is a single file at the root of the project called pyproject.toml, which is Python's agreed-upon place for tool configuration.

# pyproject.toml [tool.pytest.ini_options] minversion = "8.0" testpaths = ["tests"] addopts = ["-ra", "--strict-markers", "--strict-config", "-v"] markers = [ "unit: fast, pure Python, no I/O", "api: FastAPI TestClient, uses test DB", "e2e: Playwright, requires running server", ]

Markers are labels you stick on tests so you can run subsets on demand. A test tagged @pytest.mark.unit runs when you type pytest -m unit; add -m "not e2e" and every slow browser test is skipped. This is what makes tiered CI possible — unit tests on every save, everything on every merge, the slowest tests overnight — and it's a real interview signal to be able to show a suite designed around it.

addopts are default flags pytest applies automatically. Each of the four above earns its place. -ra summarises everything the run didn't pass, so silently-skipped tests can't hide. --strict-markers turns a typo like @pytest.mark.uint into an error instead of a silently-ignored decoration. --strict-config does the same for typos in the config file itself. -v prints each test name as it runs, so a hang tells you exactly which test hung. All four share one philosophy:

Fail loudly, fail early. A test framework that quietly ignores your mistakes is worse than useless — it gives you confidence that isn't earned.

This philosophy has a concrete payoff. Early in the setup I mistyped miniversion instead of minversion. With --strict-config in place, pytest refused to run and named the exact typo. Fix cost: 30 seconds. Without it, pytest would have silently used the default and the config would have been quietly lying to me for months. The tripwire cost nothing and paid immediately.

05 Layer 1 — Unit tests: the foundation

A unit test exercises one function, in isolation, with no database, no network, no browser. It runs in milliseconds. If it fails, the failure names exactly what broke. This is the fastest, cheapest, most focused kind of test — and where the majority of a healthy suite lives.

The best first target in any codebase is a pure function: one that takes inputs, returns an output, and touches nothing else. In todo-companion, that function is _advance_due. When you check off a recurring task, the app calls it to compute the task's next due date. It's pure date arithmetic — three lines of logic and a library call — and it silently powers every recurring habit in the app.

Every unit test in the world, no matter the language, follows the same three-part shape: Arrange, Act, Assert. Once you see it, you cannot un-see it. Tap a section below.

Six tests came out of this pattern for _advance_due, and each one taught a distinct QA concept. Daily and weekly cases covered the happy path. Monthly across a year boundary covered boundary value analysis — the practice of pointing tests at the edges where bugs love to hide. A Jan 31 + one month case covered a characterisation test, which locks in the behaviour of a library you don't control (here, dateutil's decision to clamp Feb 31 to Feb 28). A "recurrence = none" case covered the negative path. A zero-interval case covered the function's defensive clamp. Six tests, six named ideas, all running in about two hundred milliseconds.

All six passed on the first run — which raised the more uncomfortable question: would they actually catch a bug if one appeared? A green suite proves the tests passed. It does not prove the tests would fail when they should. The only way to know is to break the code on purpose and watch a test fail. This is called mutation testing, and doing it by hand a few times builds the intuition of "would my test have caught the bug I'm worried about?"

I introduced a mutation: timedelta(days=interval + 1). The daily test failed with a beautifully clear diff:

AssertionError: assert date(2026, 9, 6) == date(2026, 9, 5)

Left side: what the code returned. Right side: what the test expected. The diff tells you what the bug did. Then I tried a subtler mutation: removing the max(1, …) clamp on the interval. All six tests still passed. Not because the tests were wrong — because none of them used a negative interval. The gap only revealed itself under mutation, and I added a seventh test to close it. That's mutation thinking in miniature: write reasonable tests, poke the code, discover gaps, close them.

06 Layer 2 — API tests: the contract

Unit tests proved one function works. But todo-companion's HTTP endpoints — POST /api/tasks, PATCH /api/tasks/{id}, and so on — are the actual contract the frontend depends on. If someone (probably future me) breaks the JSON shape, or forgets to persist a field, unit tests will not notice. That's what API tests are for.

FastAPI ships with a TestClient that lets tests speak to the app directly, in-memory, without starting a real server or opening a port. A test looks like client.post("/api/tasks", json={"title": "buy milk"}), and the response comes back in about a millisecond. This is called an in-process API test: it tests the app just below the network layer, fast enough to run on every save.

The interesting part isn't the requests. It's test isolation — the hardest problem in testing any stateful system. The app opens a connection to data.db at import time. If tests hit that database, test 1 pollutes test 2 pollutes test 3, and by mid-morning your real todo list has fifteen entries called "buy milk". Every test must run against a fresh, empty database it fully owns.

The mechanism is a special SQLite connection string — sqlite:///:memory: — that lives entirely in RAM. No file, no persistence, gone when the connection closes. Combined with SQLAlchemy's StaticPool, which forces every request to share the same in-memory connection, we get a fresh database per test that vanishes when the test ends.

# tests/api/conftest.py @pytest.fixture def test_engine(): engine = create_engine( "sqlite:///:memory:", connect_args={"check_same_thread": False}, poolclass=StaticPool, ) SQLModel.metadata.create_all(engine) yield engine engine.dispose() @pytest.fixture def client(test_engine, monkeypatch): monkeypatch.setattr(app_module, "engine", test_engine) return TestClient(app_module.app)

Two fixtures — pytest's mechanism for shared setup and teardown. The first spins up a fresh in-memory database for one test. The second uses monkeypatch — a pytest tool that temporarily swaps an attribute for the duration of a test and puts it back automatically — to point the app at that fresh database instead of the real one. Both fixtures use the yield pattern: everything before yield is setup, everything after is teardown, and teardown runs even if the test fails.

With the fixtures in place, the tests themselves became short. Six covered the endpoints: create returns an id and writes to the database (the second half of that assertion — verifying the side effect, not just the response — is the one beginners skip and the one that catches silent-save bugs); list returns tasks in the right order; patching a task to "done" sets the timestamp; patching a recurring task advances its due date instead of closing it; delete cascades to subtasks; and a non-existent id returns 404 instead of crashing. Six tests, another five hundred milliseconds of runtime, and an entirely new class of bug now impossible to ship.

Worth noting: the recurring-task behaviour is now tested at two layers — as a pure function (Layer 1) and as a live HTTP round-trip (Layer 2). This isn't redundant. If Layer 1 passes and Layer 2 fails, the logic is fine but the wiring is broken. That diagnostic power — knowing which layer failed tells you where to look — is exactly why the pyramid exists.

07 Layer 3 — End-to-end tests: the whole stack

Unit and API tests verify the pieces. But a user doesn't call your endpoints — they open a browser, type in an input, click a button, and expect a task to appear. End-to-end tests drive a real browser through a real user journey. They are slow, expensive, and the only tests that catch bugs like "the button is invisible because of a CSS class collision" or "the frontend forgot to re-render after the API succeeded."

Playwright is Microsoft's modern browser-automation tool — the successor to Selenium, and the one Playwright's documentation is written around. It drives Chromium, Firefox and WebKit from Python (or JavaScript, or C#) using a small, consistent API. Its killer feature is auto-waiting: expect(locator).to_be_visible() keeps re-checking for up to five seconds before giving up. Selenium's classic problem — clicking a button before it existed on the page — simply doesn't happen. That single design decision eliminates most flaky-test pain in a single stroke.

Playwright is opinionated about locators — how you find elements on a page. In order of preference: by role (get_by_role("button", name="Save"), which doubles as an accessibility check), by label, by test id (a purpose-built data-testid attribute), and only as a last resort by CSS class or XPath. Locators tied to visible content and semantics survive redesigns; locators tied to .btn-primary-v3 break the moment a designer touches the stylesheet. The right locator strategy is why a mature E2E suite can survive years of UI iteration.

For dynamically-rendered content — tasks whose text and DOM position change every test — I added two data-testid attributes to the JavaScript that renders task rows. A two-line change bought stable selectors for every future test.

An E2E suite also has to solve two logistics problems the lower layers don't. First, a real server must be running. Second, the tests must not touch the real database. Both are handled by a single session-scoped fixture that starts uvicorn in a subprocess, points it at a temp-file database via an environment variable, polls until it responds, yields the URL to every test, and terminates it at the end. "Session-scoped" means the server starts once for the whole run, not once per test — otherwise a 10-test suite would take a minute of pure startup time.

Then the tests themselves need a shape that scales. Writing page.locator("#new-task").fill("buy milk") in twenty different tests works until the day someone renames #new-task and twenty tests break at once. The industry solution is the Page Object Model: a plain Python class that owns every selector for one page or one part of the UI, exposing user-level methods instead of low-level clicks.

# tests/e2e/pages/inbox_page.py class InboxPage: def __init__(self, page): self.page = page self.task_input = page.locator("#new-task") self.quick_add_button = page.locator("#btn-quickadd") def add_task(self, title): self.task_input.fill(title) self.quick_add_button.click() def expect_task_visible(self, title): expect(self.task_by_title(title)).to_be_visible()

A test then reads like English: inbox.add_task("buy milk") and inbox.expect_task_visible("buy milk"). If the DOM changes, one file changes. The tests don't care.

Eight E2E tests covered the real user stories: adding a task, adding several in sequence, adding one with metadata, completing a task, deleting one, the "inbox is empty" state, and — the cross-layer keystone — completing a recurring task and watching it stay visible instead of vanish. That last one is the recurring-task feature verified end-to-end: click flows through Playwright → into the browser → into the JavaScript → into the API → into _advance_due → back through the response → back into the re-render → and the task is still there. Every arrow in that chain has to work. Every arrow now has a test.

— What's coming in Part 2

The interesting problems are still ahead. todo-companion's central feature — the LLM that breaks a task into subtasks — is non-deterministic. Ask it twice, get slightly different answers. Traditional "the output must equal X" testing collapses on contact with it. Part 2 covers the alternatives: property-based tests that assert shape and invariants rather than exact strings, LLM-as-judge scoring where a second model rates the first model's output, mocked-Gemini fixtures for speed, and snapshot fixtures for drift detection across model versions. Then continuous integration in GitHub Actions to run everything on every push, a set of seeded bugs with documented investigations, and an experimental AI-assisted layer — a script that generates Playwright skeletons from feature descriptions, and a self-healing selector helper that repairs broken locators by sending the DOM back to a model for a fix.

That's where the suite stops being a personal-project safety net and starts looking like something a modern QA team would build. For now, twenty tests across three layers is a good place to breathe.
