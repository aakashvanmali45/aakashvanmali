Sculpting Code out of Noise

Study notes on diffusion code models — how CodeFusion, DiffuCoder, TreeDiff and LintSeq write a program by refining all of it at once, instead of one token after another.

Forward & reverse noise · Masked diffusion · Decoding order · Coupled-GRPO · AST span masking · Edit sequences

Every code model I'd used until now writes like a typewriter: one token, then the next, never looking back. Diffusion models write more like a sculptor. They start with a block of noise the size of the whole program and chip away at all of it at once, over several passes, until code emerges. The question I set out to answer: does that actually help for code, and why?

These notes work through four papers in order: CodeFusion (EMNLP 2023), DiffuCoder (2025), TreeDiff (2025) and LintSeq (ICLR 2025). As in my other notebooks, nothing is assumed: diffusion, masking, reinforcement learning and the rest are built from scratch, with seven labs along the way. Two earlier notes connect here: tree positional encoding (for ASTs) and grammar-constrained decoding (for the other kind of "mask").

The summary I started with, and what I had to correct

My starting summary was: instead of generating left-to-right, start with noise and iteratively refine the entire program. CodeFusion at 75M parameters matched autoregressive models at 350M–175B on top-1 accuracy and beat them on top-3/top-5. TreeDiff added AST-guided noise — corrupt structurally important tokens first, denoise them last, so the model builds structure before content. The first sentence holds up. The other two needed real corrections once I read the papers:

01 What left-to-right generation can't do

A standard language model is autoregressive (AR): it predicts token 1, appends it, predicts token 2 given token 1, and so on. Formally it factorizes the probability of a program into a chain:

Autoregressive factorizationp(y) = p(y₁) · p(y₂ | y₁) · p(y₃ | y₁, y₂) · … · p(yₙ | y₁ … yₙ₋₁)

This works astonishingly well, but it has a built-in constraint that CodeFusion's paper opens with: imagine a developer who can only ever change the last line they wrote. Once an AR model commits to a token, that token is permanent. If it picks the wrong function name early, everything afterwards has to live with it. It also means the model can't sketch the shape of a function — its signature, its return statement — and fill in the middle later, which is how many people actually write code.

There are workarounds within AR: sample many programs and pick the best, or use beam search. But samples from one AR model tend to look alike. Diversity matters: if you can test five candidates, five near-copies are worth little more than one. That diversity point comes back with CodeFusion.

02 Diffusion from zero: add noise, learn to remove it

Diffusion models made their name in images. The idea fits in two sentences. First, take real data and gradually destroy it by adding noise over many small steps, until nothing recognizable is left — this is the forward process, and it needs no learning. Then train a neural network to undo one step of that destruction — the reverse process. To generate, start from pure noise and apply the learned undo step over and over.

The two processesforward (fixed):   x₀ → x₁ → x₂ → … → x_T   clean program → pure noise
reverse (learned): x_T → … → x₂ → x₁ → x₀   noise → program, one denoising step at a timet is the timestep: t = 0 is clean data, t = T is pure noise. Training samples a random t, corrupts a real example to that level, and asks the network to recover it.

The key difference from AR: at every reverse step, the network sees and updates the whole sequence at once. Nothing is permanent until the end. That's the sculptor, not the typewriter.

Two ways to add noise to text

Images are continuous — you can add a little Gaussian noise to a pixel. Tokens are discrete — there's no "slightly noisy return". Text diffusion splits into two families on exactly this point:

FamilyWhat "noise" meansWho uses it
ContinuousTurn each token into its embedding vector, add Gaussian noise to the vectors, and at the end map vectors back to tokens.CodeFusion, and earlier text models like Diffusion-LM and GENIE
Discrete (masked)Replace tokens with a special [MASK] token. More noise means more masks; pure noise means every token is masked.LLaDA, Dream, DiffuCoder, TreeDiff

Drag the noise level in the lab to see both kinds of corruption on the same line of code. In the continuous version, each token's vector drifts, and the nearest-token readout starts returning wrong tokens. In the masked version, tokens simply disappear.

Both pictures share one important property: at a middle noise level, part of the program is still visible, and the network learns to use that visible part to fill in the rest — in any order, from either side. That's how a diffusion model learns that return usually appears near the end of a function even before it knows what comes before it.

Two different "masks". In my grammar-constrained decoding notes, a mask meant setting a token's score to −∞ so it can't be chosen. Here, [MASK] is a token placed in the sequence, meaning "unknown — fill me in". Same word, different idea. The two can even be combined: constrain which tokens may fill a [MASK].
03 Masked diffusion: deciding what to reveal first

Masked diffusion is now the dominant family for large text diffusion models, so it's worth understanding how one actually writes. Generation starts with a canvas of, say, 256 [MASK] tokens after the prompt. Then, at each step:

One step of masked diffusion decoding1. Run the network once on the whole canvas → a prediction for every masked position
2. Pick some of those positions to commit (fill in for good)
3. Leave the rest as [MASK] and repeatThe most common rule for step 2 is "low-confidence remasking": commit the positions the model is most confident about, keep the rest masked.

Two dials control everything. Which positions to commit determines the generation order — nothing forces it to be left-to-right. How many to commit per step trades speed for quality. One token per step means as many network calls as an AR model. Several per step is faster — but tokens committed in the same step are predicted independently of each other, so if they depend on one another, they can disagree.

The lab makes both dials concrete. The model is a toy with scripted confidences, but the failure it shows is real: commit two dependent tokens in the same step and you can get def is_even(n): return x % 2 == 0 — each token plausible on its own, the pair inconsistent.

Confidence-based decoding tends to wait for the parameter name before writing n in the body, simply because the body's n is uncertain until then. Random order doesn't wait. And the more tokens you commit per step, the more often two dependent tokens land in the same step — try random order at 3 or 4 per step a few times.

04 CodeFusion (2023): continuous diffusion for code

CodeFusion (Singh, Cambronero, Gulwani, Le, Negreanu and Verbruggen at Microsoft; EMNLP 2023) was the first diffusion model for turning natural-language requests into code. It belongs to the continuous family, and its main idea is a fix for that family's weak spot.

The problem with rounding

Earlier text diffusion models denoised embeddings and then, at the very end, mapped each position to its nearest vocabulary token — independently. For prose, a slightly-off word is fine. For code, independent rounding easily produces print(x or a misspelled variable, and the program won't parse. CodeFusion measured this directly: only 24.2% of GENIE's top Python outputs were syntactically valid, against 67.6% for CodeFusion.

The architecture

CodeFusion has four parts, with 75 million parameters in total:

PartJob
EncoderReads the English request and turns it into vectors (a pre-trained CodeT5 encoder).
DenoiserA 10-layer Transformer. Given the noisy program embeddings, the timestep and the encoded request, it predicts the noise to remove. Runs once per diffusion step.
DecoderA 6-layer Transformer that runs once, after denoising finishes. It sees all the denoised positions together (full self-attention) plus the request.
Classification headTurns each decoder output into a token. No search — it takes the most likely token at each position.

The decoder is the fix. Instead of rounding each position on its own, every final token is chosen with knowledge of every other position. Inference starts from Gaussian noise and runs 1,200 denoising steps; the ablations show that replacing the decoder with plain rounding costs roughly 3–10 points, depending on the language and the rounding variant.

Pre-training on code-aware noise

Before fine-tuning on (request, code) pairs, CodeFusion pre-trains the denoiser and decoder on code alone with two tasks. One is plain unconditional generation. The other adapts a task called continuous paragraph denoising to code: it adds noise only to identifiers and language keywords — variable names, function names, for, if. The model has to reconstruct exactly the tokens that carry a program's meaning from the context around them. Removing either pre-training task hurt every language.

This is the closest any of the four papers comes to my original "structure-aware noise" intuition — and it's in CodeFusion, not TreeDiff. CodeFusion chooses which kind of token to corrupt during pre-training; it still doesn't impose an order at generation time.

The headline result, and why diversity matters

CodeFusion was tested on three tasks: Python snippets from Stack Overflow (CoNaLa), one-line Bash commands, and Excel conditional-formatting rules. The top-1 / top-3 / top-5 columns ask: is a correct answer among the model's first one, three or five suggestions?

The fine print

Reading the paper closely, a few details change how strongly I'd state the result:

The Python metric isn't execution. Python was scored with CodeBERTScore, which measures similarity to a reference solution using a neural model. Exact-match accuracy for Python was around 5% for everyone (CodeFusion 5.1% top-1). Bash used template matching; only the Excel rules were scored by actually running them.

The giant models weren't fine-tuned. GPT-3, ChatGPT, StarCoder and CodeT5+ were prompted with five similar examples; the fine-tuned baselines were 350M–770M. "Beats 175B" means "beats 175B used few-shot".

Short programs only. The output canvas was 128 tokens, and the authors note that CodeFusion struggles with longer programs and long-range dependencies. Inference took about 2.3 seconds per example, with latency growing quadratically with length.

The preprint was withdrawn. The arXiv version was withdrawn within a week of release. The notice says the authors had relied on a news article for information they couldn't verify — widely understood to be the parameter count it listed for ChatGPT. The EMNLP version lists ChatGPT's size as "Unknown". This doesn't affect CodeFusion's own numbers, but it's worth knowing when citing it.

05 DiffuCoder (2025): a 7B masked diffusion coder, and RL for it

Between 2023 and 2025, masked diffusion scaled up. LLaDA and Dream showed 7–8B masked diffusion models could roughly match AR models of the same size. Commercial systems like Inception's Mercury and Google's Gemini Diffusion advertised strong coding at high speed. DiffuCoder (Gong, Zhang, Zheng, Gu, Jaitly, Kong and Zhang, from Apple and the University of Hong Kong) asks two questions: how do these models actually decode code, and how do you improve them with reinforcement learning?

The model

DiffuCoder starts from an AR model, Qwen2.5-Coder-7B, and converts it into a masked diffusion model through continued training — about 130 billion effective tokens of code. Then come instruction tuning (436K examples) and a reinforcement learning stage on 21,000 hard problems with test cases.

Two things stand out. The base diffusion model is on par with its AR parent. But instruction tuning helped the AR model far more than the diffusion model, on the same data — a gap the authors use to motivate the RL work. Diffusion for code is competitive, not yet ahead.

How left-to-right is it, really? AR-ness

DiffuCoder defines two measures of decoding order, both equal to 1 for a pure AR model:

MeasureQuestion it asks at each step
Local AR-ness@kIs the newly committed token the immediate successor of the previous k committed tokens — writing a contiguous run?
Global AR-ness@kIs it one of the k leftmost still-masked positions — filling from the front?

The lab in Section 03 computes the k = 1 versions live. The findings: diffusion models are fairly left-to-right but not fully, and models converted from AR ones keep more of that habit. Code is decoded less left-to-right than maths (lower and more variable global AR-ness): the model sometimes writes later parts of a program before earlier ones, a bit like a programmer jumping around a file. And in a diffusion model, temperature changes the order, not just the words. At temperature 1.2, generation order becomes much more varied, and pass@10 rises substantially.

They also found an entropy sink: on the first decoding step, the model is most confident about the positions immediately after the prompt, giving an L-shaped confidence curve. That's why confidence-based decoding still drifts left-to-right.

Reinforcement learning, from zero

Reinforcement learning with verifiable rewards works like this for code: the model writes several solutions to a problem, each is run against tests, and the ones that pass get "reinforced" — their probability is pushed up. GRPO (Group Relative Policy Optimization) does this per problem: generate a group of G solutions, score each, and give each solution an advantage equal to its score minus the group's average. Above-average solutions are pushed up, below-average ones down.

Pushing a solution's probability up requires computing that probability. For an AR model that's easy — the chain rule from Section 01, one forward pass. A masked diffusion model has no such chain. Its log-probability can only be estimated: mask some tokens, ask the model to predict them, and use the cross-entropy on those positions. That estimate is noisy, and it only scores the tokens that happened to be masked.

Coupled-GRPO: complementary masks

DiffuCoder's fix is simple and clever. For each solution, draw one random mask, then use its exact complement as a second mask. Run the model on both. Every token is masked — and therefore scored — in exactly one of the two passes. No token is skipped and none is double-counted. Statistically, this is the "antithetic variates" trick for reducing variance. Try it below: compare two independent random masks with a coupled pair.

With coupled-GRPO, EvalPlus rose by 4.4 points (63.6 → 67.9) from only 21K training problems. Baselines that used a single fully-masked pass or two independent masks trained unstably. A side effect I didn't expect: after RL, the model became less left-to-right, and lost less accuracy when decoding at double speed (half the steps) — RL made it better at parallel decoding.

06 TreeDiff (2025): masking whole syntax subtrees

TreeDiff (Zeng and colleagues, led from the University of Connecticut; a workshop paper at ACL 2026) starts from a criticism of how masked diffusion models are trained: they mask tokens independently at random. In code, that scatters masks across syntactic units — half a condition here, one argument there. The model rarely has to reconstruct a whole loop, call or condition, which is exactly what it must do when generating.

The method: mask AST spans, keep the budget

TreeDiff parses each training program into its abstract syntax tree (the same AST from my tree-encoding notes). Every node covers a span of tokens. Instead of masking tokens one by one, it masks entire spans: a whole for loop, a whole function call. The subtle part is keeping the overall amount of masking the same as random masking, so the comparison is fair. If random masking would hide each token with probability ε, TreeDiff masks a span of length ℓ with probability:

Span masking probabilitypᵢ = 1 − (1 − ε)ℓᵢThe probability that at least one of the span's ℓ tokens would have been masked under token-wise masking. In expectation, the same number of tokens gets masked; they just come in whole syntactic units. Spans shorter than two tokens are skipped, and leftover budget is filled with random tokens.

Masking is applied during training. Generation still works like any masked diffusion model. Compare the three strategies the paper tested in the lab — including the one closest to my original summary.

What they found

TreeDiff fine-tuned LLaDA-8B-Instruct (an 8B masked diffusion model) on 150,000 examples from OpenCodeReasoning, each with a problem, a reasoning trace and a solution. Reasoning text got ordinary token masking; code got the AST strategy. Pass@1 results:

(The "@512/@1024" is the generation length. The final version of the paper reports a 13.3% relative improvement over random masking.)

Where my summary went wrong. The middle row is the strategy closest to "corrupt structurally important tokens more": control flow masked with probability 0.60, conditionals 0.58, calls 0.42, everything else 0.15. It did worse than plain random masking on MBPP and on long HumanEval generations. What helped was keeping syntactic units intact — masking a whole unit or none of it. And nothing in TreeDiff sets a generation order. "Build the structure before the content" is an appealing idea, and DiffuCoder's lower AR-ness on code hints that models do plan non-sequentially. But it isn't what TreeDiff does or measures.

Some caution on the numbers too: the gains are a few points on 164 HumanEval problems, from one base model, in a workshop paper. It's a promising, simple idea rather than a settled result.

07 LintSeq (2025): the same intuition, without diffusion

LintSeq (Piterbarg, Pinto and Fergus at NYU; ICLR 2025) is the odd one out, and I think it's on this list because it reaches a similar goal by a completely different route. People don't write programs top to bottom in one pass — they write a skeleton and grow it. Diffusion models capture that by refining a whole canvas. LintSeq keeps an ordinary AR model but changes its training data: instead of "instruction → full program", it trains on "instruction → a sequence of edits that builds the program". The authors say directly that they were inspired by discrete diffusion.

Where the edit sequences come from

Real edit histories are scarce, so LintSeq generates synthetic ones from finished programs, in two phases:

Backward sampling. Start from the finished program. Delete a random line. Run a linter — a static checker that flags errors like undefined variables. If the deletion broke other lines (say, you deleted total = 0 and a later line uses total), delete those too, and repeat until the linter is clean. Keep going until the program is empty. Every intermediate program is error-free.

Forward edits. Reverse the list — empty program first, finished program last — and express each step as a Unix-style diff. Every diff is insertions only. The model is fine-tuned to output these diffs one after another, separated by a special <|diff|> token. Applying them in order rebuilds the program.

What it achieved

The authors pre-trained tiny code models from scratch (150M and 400M parameters) and fine-tuned them on the same instruction data, once as full programs and once as LintSeq edit sequences. For the 150M model, HumanEval pass@1 went from 9.1% to 12.8%, roughly matching code models twice its size, such as Codex-300M. On larger general models (Gemma 2, Phi-3, Llama 3.1; 2.6B–14B), pass@1 stayed level or improved slightly, but pass@k at larger k improved a lot. Phi-3-Mini's HumanEval pass@50 rose from 62.2% to 87.3%. The theme is the same as CodeFusion's: more diverse samples, so repeated sampling pays off more per unit of compute.

The linter matters. Replacing linter-guided deletion with random deletion ("RandSeq") cut pass@1 by 24–30% and produced far more broken code — the same lesson as TreeDiff: corrupting along the program's real structure teaches more than corrupting at random.

What I'd tell myself at the start

Diffusion for code is real and competitive, but the story is more about diversity and flexibility than about beating AR models outright. CodeFusion's honest win is top-k on short tasks. DiffuCoder shows a 7B diffusion coder can match its AR parent, and that RL needs to be redesigned for it. Three threads run through all four papers. First, diversity is the recurring advantage, visible as top-k and pass@k gains. Second, order is a choice: diffusion models decide what to write first, and code is where they deviate most from left-to-right. Third, structure-respecting corruption beats random corruption, whether it's CodeFusion's identifier noise, TreeDiff's subtree spans or LintSeq's linter-guided deletions.

The costs are real too: a fixed-length canvas to fill, many network calls unless you commit several tokens per step (with the consistency risk the Section 03 lab shows), and harder likelihoods for RL. And, after my corrections, the claim I'd now defend is narrower than the one I started with: structure-aware training noise helps. Whether these models build structure before content is still an open question, not a finding.
