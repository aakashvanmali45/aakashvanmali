The Radar Operator's Problem

Why a 90%-accurate model can be worthless, and why the metric built for WWII radar screens is still the best way to judge whether a classifier can tell signal from noise.

AUROC · ROC · Precision · Recall · F1 · Balanced Accuracy

In 1941, radar operators on the English coast stared at flickering screens trying to answer one question, fast: is that blip an incoming aircraft, or noise — a flock of birds, a weather front, a ghost in the electronics? Set your sensitivity too high, and you scramble fighters at every seagull. Set it too low, and a real bomber slips through. Every operator was, without knowing it, choosing a threshold.

That problem got a name — Receiver Operating Characteristic, or ROC — and decades later it became one of the most useful ideas in machine learning. Today your spam filter, your fraud detector, and your defect classifier all face the exact same dilemma the radar operators did. This is a field guide to how we measure whether they're any good at it — and where the usual scoreboard, accuracy, quietly lies to you.

01 The problem with a single number

Say you're building a classifier and your test set has 90 positive samples and 10 negative ones. Now imagine the laziest possible model: it never looks at the input. It just predicts positive, every single time.

It never once identifies a negative case — the class you probably cared about most, whether that's fraud, a defective part, or a rare disease — and it still walks away with a 90% score. Accuracy is only honest when your classes are roughly balanced. The moment one class dominates, a model can look brilliant while being completely blind to the thing you built it to catch.

So we need metrics that look inside the confusion matrix instead of collapsing it into one number.

02 Precision and recall enter the room

Every prediction a binary classifier makes lands in one of four buckets: a true positive (correctly flagged), a false positive (false alarm), a true negative (correctly ignored), or a false negative (missed). Precision and recall each ask a different question about those buckets.

Precision = TP / (TP + FP)
Of everything I flagged as positive, how much of it was actually positive? — a measure of how much you trust an alarm.
Recall = TP / (TP + FN)
Of everything that was actually positive, how much did I actually catch? — a measure of how much slips past you.

Both are computed at one fixed threshold — the cutoff score above which the model calls something "positive." That's exactly their strength and their limitation: they tell you how the model behaves at the operating point you chose, but say nothing about whether a better operating point exists.

03 F1: a photograph, not a movie

Precision and recall usually trade off against each other: flag more things positive and recall climbs while precision falls, and vice versa. F1 is the harmonic mean of the two, a single number that punishes you if either one is weak.

F1 = 2 × (Precision × Recall) / (Precision + Recall)
A balanced score of a model's performance — but still tied to whatever threshold you picked to compute precision and recall.

That's the catch. F1 is a photograph of performance at one threshold, not a movie of how the model behaves across all of them. Change the threshold, and F1 changes too — sometimes a lot. If two models are being compared and each was evaluated at its own "best" threshold, F1 alone can't tell you which one is fundamentally better at separating the classes, only which one you tuned better.

That's the gap AUROC was built to fill: a score for how well a model separates the two classes, independent of any single threshold you happen to choose.
04 Enter the ROC curve

Instead of freezing the threshold and reporting one point, the ROC curve asks: what happens at every possible threshold, from "flag almost nothing" to "flag almost everything"? At each threshold we plot two rates:

TPR (True Positive Rate / Recall) = TP / (TP + FN)
Of the real positives, what fraction did we catch at this threshold?
FPR (False Positive Rate) = FP / (FP + TN)
Of the real negatives, what fraction did we wrongly flag at this threshold?

Plot TPR on the y-axis against FPR on the x-axis as the threshold sweeps from 1 down to 0, and you get a curve. At threshold = 1, nothing is flagged: TPR = FPR = 0, bottom-left corner. At threshold = 0, everything is flagged: TPR = FPR = 1, top-right corner. Everything in between traces out how the model trades false alarms for catches as you loosen the trigger.

A ROC curve: each point is one threshold's (FPR, TPR). The diagonal is what a coin flip achieves.

A model with zero skill — random guessing — produces the diagonal line: whatever false-alarm rate you accept, your catch rate is exactly the same. A useful model bows up toward the top-left corner: high catch rate, low false-alarm rate, for as much of the sweep as possible.

05 AUROC: the area under everything

AUROC — Area Under the ROC Curve — collapses that entire curve into a single number between 0 and 1. It has a wonderfully clean interpretation:

AUROC is the probability that a randomly chosen positive example scores higher than a randomly chosen negative example. Pick one item from each class, ask the model to score both — AUROC is how often it ranks the positive one above the negative one.

Because it's built from TPR and FPR summed across every threshold, AUROC doesn't care which threshold you'll eventually deploy at. It only asks whether the model's scores separate the two classes at all — which makes it especially useful when you don't yet know your operating threshold, or when you're comparing two models before either has been tuned.

06 When the minority class matters equally

Sometimes you still want a single accuracy-like number — for a report, a dashboard, a quick health check — but you don't want it distorted by class imbalance the way plain accuracy is. Balanced accuracy fixes that by giving every class equal say, regardless of how many samples it has:

Balanced Accuracy = (Recallclass 1 + Recallclass 2) / 2
Each class contributes equally — a large class can no longer dominate the score.

Revisit the lazy "always predict positive" model from the start of this piece: recall on the positive class is 100%, recall on the negative class is 0%.

90%
Plain accuracy
50%
Balanced accuracy

Balanced accuracy immediately reveals what plain accuracy hid: this model is exactly as good as a coin flip once you stop letting the majority class carry it. That's why it's the default sanity check in domains like anomaly and defect detection, where the thing you actually care about is almost always the rare class.

None of these metrics is "the best" one in isolation — they answer different questions. Accuracy asks how often am I right, overall? Precision and recall ask which kind of mistake am I making? F1 asks can I balance those mistakes at one setting? And AUROC asks the radar operator's original question: if I had to sweep the dial from paranoid to careless, how well does this system tell signal from noise the whole way through?
